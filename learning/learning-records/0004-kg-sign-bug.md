# 0004 — 教学发现：引擎 pose_metrics 主销交点符号 bug

日期：2026-08-22（第 5 章备课实验中发现）

## 现象

引擎设计位指标：scrub = 229.0 mm、trail = −54.7 mm（负拖距配正后倾，物理不通）。

## 根因（一行符号）

主销-地面交点 kg 的参数化：

```text
前端（正确）:  t0 = (cp.z − ubj.z) / (lbj.z − ubj.z)   分母 = −290 → t0 = +1.586 → kg 在地面 z≈−5
引擎（错误）:  dz = ubj.z − lbj.z (= +290)             ← dz 同时供 kpi/cast 使用（那边符号恰好自洽）
               t0 = (cp.z − ubj.z) / dz                分母 = +290 → t0 = −1.586 → kg 在 z=+914.8（UBJ 上方！）
```

S2-5 移植前端公式时，把 t0 的分母统一用了 dz，符号翻转，kg 落到主销轴错误一端。

## 证据链

1. 手算：t0=−1.586 → kg=(587.8, −54.6, **914.8**)，scrub=cp.x−kg.x=229.0、trail=kg.y−cp.y=−54.7 —— 与引擎输出逐位一致（确认输出即 bug）；
2. 前端真实浏览器（playwright）：kg.z=−12.3（地面）、scrub=**54.5**、trail=**+24.9**（正后倾配正拖距，物理自洽）；
3. 正确值手算复核：t0=+1.586 → kg=(762.2, +24.6, −4.9) → scrub≈54.6、trail≈+24.6 ✓。

## 影响

- scrub/trail 两项错误（含 /api/v3 全部端点与前端引擎面板展示）；
- cam/toe/kpi/cast/rc_h 不受影响（不用 kg）；
- 与转向输入轴裂缝（第三讲 3.5）相反：这次是**引擎移植错、前端对**。

## 修复（待用户解除开发暂停后执行，一行）

`chassis.py`/`v3service.py` 的 pose_metrics：`t0 = (cp[2] - ubj[2]) / dz` → 除以 `-dz`（或分母改 `lbj[2] - ubj[2]` 与前端一致）；同步 test_v3 断言（scrub≈54.6、trail≈+24.6）。

## 教学价值

第 5 章的活教材：逐行对账 + 手算验证 = 真实审计流程；"数值能算出来"与"数值是对的"之间的鸿沟正是量纲/量级/物理一致性检查要填的。
