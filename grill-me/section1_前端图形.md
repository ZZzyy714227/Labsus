# 参考答案（方向一）

**1.** 合格要点：Three.js 用于第一代 3D 预览（线框 + 小球，LineBasicMaterial/MeshLambertMaterial）；放弃的真实动因通常是组合拳：单文件双击即用的部署诉求 vs Three.js 的依赖引入（CDN importmap 断网不可用 / npm 需构建链）；渲染本身不是瓶颈。能给出具体版本、引入方式和至少一次缓解尝试（如按需渲染）即为合格。承认"Three.js 没死在性能上，死在部署形态上"是最诚实的答案。

**2.** 合格要点：确认全手写——正交视图 `dot(p,bx)` 线性投影，透视视图针孔模型 `f=dist/z`；近平面 z<80 直接丢弃点。线段穿近平面确实会出反向飞线/丢线，正确修法是对线段两端做参数插值裁剪（t = (80 - z0)/(z1 - z0)）；承认当前实现是 demo 级裁剪是加分项。Canvas 2D 够用因为图元是数百量级的 2D 路径，不是万级三角形。

**3.** 合格要点：能报出三代的时间线、代码规模（单文件版 348KB / 内置引擎版 216KB）、每代保留的东西（矢量数学库 add/sub/dot/cross、HP_META 硬点元数据、四视口布局是从一代延续下来的）。重构判据：allinone 双击可用（车队赛场无网）；fullchassis 对接后端满血 K&C。承认 348KB 单文件是刻意的部署取舍而非最佳工程实践。

**4.** 合格要点：拖拽时 `rebuild()` → `driveTo`：把轮心目标 Z 差分成 `min(28, ceil(|d|/4))` 步、每步 ≤4mm 延拓，中间步 maxIt=40、末步 260，tol=2e-7；这是 continuation 法——用上一步解作下一步初值，避免一步跳变大位移时投影迭代落入错误装配分支。一帧 50mm 会走 13 步左右仍在单帧内完成（JS 求解毫秒级），视觉上是即时贴合；速度极快时可能短暂显示中间姿态。拖拽全程走前端 JS 引擎，不发网络请求。

**5.** 合格要点：残差是杆长误差的 max-范数（无穷范数，单位 mm）+ 轮心 Z 驱动残差取 max；选 max 是保证最坏约束达标，代价是收敛尾部抖动、无平滑梯度。tol=2e-7mm 用于迭代提前退出，最终判定 M.ok 用 0.025mm 宽容差（投影迭代精度现实）。`(it&3)===3` 每 4 次才算残差省约 75% 残差计算。JS 投影迭代解等式约束（杆长=定值），Python TRF 解非线性最小二乘（残差平方和），两者问题定义不同、残差范数不同，parity 脚本比对的是同输入下最终节点坐标/定位角，容差需自己能报出。

**6.** 合格要点：机构数据全局单份（SIM.FR/RR/FL/RL），四视口只持相机参数（VW 数组：s/cx/cy/az/elv/dist）；联动 = 数据共享，不是消息广播。每帧 `loop()` → `simulate(dt)` → `drawAll()` 四视口全量重绘 → `updateReadouts` → `drawPlots`，无脏区。K&C 扫掠在 `updateSweeps` 里 140ms 节流 + 45 步，与拖拽同线程但被节流保护；拖拽期间扫掠最多每 140ms 插入一次约几十 ms 的批量计算，实测帧率会抖但可接受——能主动说出"没做 Web Worker 隔离是已知短板"加分。

**7.** 合格要点：PICK 在绘制阶段由 ND 图元投影时填充（视口相关）；投影 null（近平面后）的点不进 PICK 或拾取异常，是已知盲区。屏幕重叠时选距离最近者，无深度消歧——正视图里前后轮硬点重叠会选错，靠镜像开关（show.mirror）规避。透视视口禁拖的原因：屏幕位移 → 世界位移需要除以深度 z，透视下同一像素位移对应不同深度的不确定位移，正交视图有固定基向量 bx/by 和比例 s 才能唯一反解。

**8.** 合格要点：`da/db` 是像素位移除以 s（px/mm 比例）得视图平面内毫米位移，再按 bx/by 基向量合成世界向量；镜像侧 X 翻号因为左右对称硬点的世界 X 与屏幕 X 方向相反（Y/Z 轴向不随镜像翻转）。滚轮用幂函数 `1.0015^(-deltaY)` 是因为滚轮 deltaY 离散值大，指数映射手感均匀且无极跳；clamp [0.02,15] 防过度缩放后拾取/拖拽数值失稳。0.1mm 量化让显示与求解输入一致，避免浮点尾数触发无意义的机构重解。

**9.** 合格要点：画家算法——图元按到相机（或视图法向）距离排序后从远到近绘制；每帧排序数百图元，Array.sort O(n log n) 完全无压力。半透明面排序敏感（透明面不写深度在 Canvas2D 里表现为叠加顺序即绘制顺序），承认存在排序错乱的已知 case（如摇臂与弹簧重叠）。能举出实例（如推杆穿过 A 臂时闪烁）并说明修法（微调排序 key / 拆分图元）为佳。

**10.** 合格要点（数字量级，允许 ±50%）：单轴模型约 20+ 节点 / 20+ 杆件；`solveKin` 典型 5–20 次迭代、几十微秒到 1ms 级；`driveTo` 大位移时 <5ms；每帧预算里求解 <2ms、四视口绘制 2–6ms、DOM 读数更新 1–2ms。FPS 统计是 0.4s 窗口计数写 `#tbFps`。内存：长期运行的主要风险是 sweep 数组与 plots 画布重建，应能说出测量手段（DevTools Memory 快照对比）。任何"没测过但很快"都判不合格。

**17.** 合格要点：图元投影 null 后，绘制层若直接解构 null 会抛错/丢线——需追认 L3 绘制路径对 null 的处理（大概率是丢线或异常），承认这是未完全处理的边界。屏幕外图元交给 canvas 原生裁剪（省 CPU 但浪费光栅化，规模小可接受）。elv clamp ±85° 正是为避开 up 向量与 fw 平行的退化（cross 趋零向量，rt 归一化爆掉）；正确通用解是相机 up 特判或四元数轨道相机。

**18.** 合格要点：`projBody` 对节点相对坐标的加权外积矩阵 A 做 polar decomposition（polarQ 迭代 14 次把 A 正交化为最近旋转 R），比 SVD 便宜且只需旋转；A 奇异 = 点集共线（病态但约束系统里不应发生）。用四元数因为迭代重定向需要连续插值与无奇异性。1e-3 质量下限防零权重除零，是数值护栏而非物理值。若 14 次不收敛，R 非正交 → 节点位置漂移 → 杆长残差增大 → M.ok=false，用户能看到求解失败标记。

**19.** 合格要点：正交视口拖拽被约束在视图平面内，法向自由度需切到另一视口补拖（三视图轮拖可覆盖 3DOF）或用数值输入框直接改坐标。这是刻意的产品取舍（视图平面拖拽手感直观）；改进方案：以硬点当前深度为切片的"拖拽平面"（视图射线 + 深度常量反解第三坐标），代价是手感歧义。`axisAtY` 用于沿轴距插值取参考点（如求某 Y 处的轴线坐标）。

**20.** 合格要点：白名单 coreLinks 是主运动学闭环（LCA/UCA/主销/转向拉杆/弹簧摇臂相关）；damper、pushrod 从动长度不进残差，因为它们是从动输出而非约束。`clamp(C/hyp,-1,1)` 在摇臂-推杆几何不可达时会把 acos 强行合法化，机构实际断裂但残差检查不到该路径——`M.ok` 仍可能 true，这是已知缺陷，应把 rocker 残差也纳入或单独告警。branch 翻转表现为机构姿态跳变/穿模；应检测相邻解的分支连续性。有真实反关节案例（如大 heave 时 UCA 反向）者可信。

**21.** 合格要点：dt clamp 0.045s 防 tab 后台节流后回前台的首帧巨 dt（否则动力学积分一步爆掉）。S.play=false 时循环仍跑（渲染视角操作、拖拽、界面刷新需要）。多 rAF 链是 stage 隔离的历史产物——stage 打开时主循环挂起只续帧，stage 有自己的 tick；代价是双 rAF 调度与切换期双写风险（代码注释里"避免双写 SIM"印证踩过）。后台节流下应以固定仿真步长 + 累积器（fixed timestep accumulator）解耦渲染帧，承认目前未做。

**22.** 合格要点：4-Post/爬坡/绕桩的动力学积分在前端 JS（stepDyn/TPHYS，简化模型，保证交互实时）；赛道瞬态在后端（simulate_track，Pacejka + 准静态内核），前端只做回放（TRK.playing + speed 倍速控制回放索引推进）。原因：赛道仿真含轮胎瞬态与整车耦合，JS 侧无该实现且无需交互级实时。stepDyn 目前绑定帧 dt（clamp 0.045），未做固定子步进是已知精度风险；前端 K&C 查表 lut 用 travel 网格线性插值喂后端，其步长（扫掠 45 步）与插值误差对力平衡的影响应能定性说出（camber/toe 曲线局部线性假设）。

**23.** 合格要点：no-cache 服务防开发期"改了 348KB 单文件但浏览器缓存不刷新"；file:// 下 fetch/引擎连接被浏览器安全策略禁（CORS/null origin），所以 allinone（内置引擎）可双击用、fullchassis（需 fetch）必须 http。兼容矩阵至少 Chrome/Edge 实测；ResizeObserver、AbortController 都是现代基线，位运算 `(it&3)` 无兼容问题——没测过 Safari 应直说。

**24.** 合格要点：工作量排序（难→易）：文字标注（WebGL 文字需 SDF/atlas 或干脆保留 2D overlay 混合层）> 线宽（WebGL lineWidth 依实现常为 1px，需三角带展开或实例化四边形）> 拾取（几十个拾取点，CPU raycast 足够，无需 GPU id-buffer）。最难的坑是文字与线宽的"2D 语义"在 3D API 里变成几何问题。结论层面应能说出"当前规模 Canvas2D 不是瓶颈，迁移收益主要是深度一致性而非速度"——为迁而迁判不合格。

**25.** 合格要点：三句精确表述参考——(a) "前端为零依赖原生实现：Canvas 2D 软渲染，手写正交/透视投影、屏幕空间拾取、四元数刚体重定向，无 Three.js/无框架"；(b) "计算引擎双实现分精度层级：JS 侧闭式投影迭代供毫秒级交互闭环，Python 侧 SciPy TRF 供高精度 K&C 与瞬态求解，两者由 parity 脚本校验坐标级一致"；(c) "四视口联动是全局机构数据共享 + rAF 重绘，硬点拖拽为 JS 侧毫秒级实时闭环；K&C 扫掠 140ms 节流、赛道仿真为异步计算后倍速回放"。能主动说出这三处区分，而不是被追问后才承认，即为高分。
