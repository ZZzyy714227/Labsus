**1. [难度4] 你简历写"三代架构重构"，第一代是 Three.js 原型。请先给结论：Three.js 到底在哪一步卡死了？**

**回答**：**Three.js 不是死于性能，是死于部署形态和开发节奏。** 第一代原型现在还在仓库里：`archive/legacy-root/web/versions/v1-dwb-web-simview.html`，17,532 字节，`three@0.160.0` 通过 unpkg 的 importmap 引入（`"three": "https://unpkg.com/three@0.160.0/build/three.module.js"` + addons 路径），外加 Tailwind CDN、lucide、Chart.js 三个 CDN 依赖，`WebGLRenderer({antialias:true})` + `PerspectiveCamera(40, W/H, 1, 30000)` + OrbitControls，场景就是线框加小球。

(a) 卡死的不是渲染也不是几何更新 API——那个规模（几十个硬点、几百条线段）Three.js 随便跑 60FPS。真正的现象是：**演示场景断网即白屏**。importmap 指向 unpkg，车队车间和赛场没有可靠网络，页面直接起不来；我当时没有引入 npm + 打包器的意愿，因为整个项目就是想保持"双击一个 HTML 就能看"的交付形态。加上 Tailwind/Chart.js 也是 CDN，脆弱依赖链一共有四条。这不是报错意义上的"卡死"，是部署意义上的。

(b) 版本 0.160.0，CDN importmap 引入，没用 npm。冲突点正如上面说的：ES Module 的 importmap 方案要求在线；npm 方案要求构建链（Vite 打包后倒是能单文件化，但当时我不想要 node_modules 和构建步骤这两层间接性）。事后看这个权衡可以重新议，但当时的决定是自洽的。

(c) 缓解手段试过：把 importmap 指向本地下载的 three.module.js——这条路其实可行，但 OrbitControls 的 addons 又引一堆内部相对导入，手工摊平很脏；也试过按需渲染（只在相机变化时 requestAnimationFrame），但那解决的是功耗不是依赖。最后判断：我要的其实是"四视口 + 正交/透视 + 屏幕空间拾取 + 毫秒级重解"，这些逻辑我反正都得自己写，Three.js 能替我做的只有矩阵和 WebGL 封装，而我的图元量级用 Canvas 2D 完全够。于是第二代直接手写投影，零依赖。复盘：用 CDN importmap 做严肃工具的前端是我第一代的真实失误，教训是"依赖引入方式要匹配部署形态，而不是匹配开发时的方便"。

**2. [难度5] 你的"原生单文件渲染"到底原生到什么程度——投影矩阵是不是你自己推的？**

**回答**：**是，全部手写，零运行时依赖。** `dwb-pro-fullchassis.html` 里没有一个 Three.js：正交视图在 `P2()` 里是 `v.w/2 + (dot(p,v.bx)-v.cx)*v.s`、`v.h/2 - (dot(p,v.by)-v.cy)*v.s`——沿基向量 `bx/by` 的线性投影加平移缩放；透视视图是针孔模型：`q = p - eye`，`z = dot(q, fw)`，`f = v.dist/z`，屏幕坐标 `dot(q,rt)*f*v.s`、`-dot(q,up)*f*v.s`。拾取是屏幕空间距离场（`pickNode`），刚体姿态是手写四元数代数（`qMul/qNorm/qAA/qM`）+ `polarQ` 极分解迭代。

(a) 裁剪——这里我要先纠正题目的一个前提。近平面确实是 `z < 80`（毫米制，直接 `return null`），但 `L3()` 图元在绘制层**有 null 检查**：`drawView` 里对 `"l"` 型图元是 `const A=P2(v,o.a),B=P2(v,o.b); if(!A||!B)continue;`——端点任一为 null 整条线**跳过**；对 `"p"` 型折线是 `if(!Q){st=false;continue;}`——断笔重开。所以实际行为**不是反向飞线，而是整根杆件消失**。这仍然是缺陷，甚至某种意义上更糟：拖拽/旋转让杆件穿越近平面时会"啪"地闪没，而不是被正确裁剪。正确修法我很清楚：对线段做参数化近裁剪，`t = (80 - z0)/(z1 - z0)`，把穿越端插值重投到近平面上，保留前半段。我没做，因为透视视口在我产品里是观察视图（禁止拖硬点），穿近平面的频率低，我把它归为已知边界缺陷，优先级排在机构求解正确性之后。这是诚实的 demo 级裁剪，我不给它贴"完整渲染器"的标签。

(b) 不用 WebGL 的原因：我的每帧图元量级是几百条 2D 路径（buildScene 一次性生成模型空间图元，四视口各投影一遍），Canvas 2D 完全在帧预算内；节点规模 15 硬点 × 4 角 = 60 节点，不是万级三角形场景。瓶颈测过：`solveKin` 内部有 `performance.now()` 计时存进 `M.ms`，绘制侧用 DevTools Performance 面板看过，四视口全量重绘 + 读数更新合计约 3–7ms，60FPS 有余量。Canvas 2D 的真实短板是**没有深度缓冲和线宽抗锯齿质量**，不是速度——这句话我在第 24 题还会展开。

**4. [难度4] 你说"实时联动"——请先定义"实时"。拖住一个硬点从松开鼠标前，机构解到底是每帧重解，还是插值？**

**回答**：**是每帧真重解，不是插值；且走的是前端 JS 内置引擎，不发任何网络请求。** `mousemove` 处理器里每动一次就更新 `S[axis].hp[id]` 然后 `rebuild()` → `refreshDerived` → 下一帧 `simulate()` 里对四个机构各跑一次 `driveTo`。

(a) 代码事实与题目给的数字一致：`driveTo(M, targetZ, rack, axis)` 里 `const d=targetZ-cur, steps=Math.min(28, Math.max(1, Math.ceil(abs(d)/4)))`——目标轮心 Z 差被分成**最多 28 步、每步最大 4mm** 的延拓序列；循环里 `solveKin(M, cur+d*s/steps, s===steps?260:40, 2e-7)`——**中间步迭代上限 40 次，最后一步 260 次**，tol 都是 2e-7（mm）。

(b) 为什么分步：这是 continuation（路径延拓）式求解。`solveKin` 的投影迭代是局部收敛的，初值依赖上一步的姿态；一步跳 50mm 大位移时，迭代很容易收敛到**错误的装配分支**（比如摆臂翻过死点、摇臂跳到另一侧），或者干脆不收敛。用上一步解作下一步初值，每步只走 4mm，解轨迹是连续的，分支稳定性由路径连续性保证。末步给 260 次是因为它要承担最终精度（res<0.025mm 判 M.ok），中间步只需把姿态"带到位"，40 次够了。

(c) 一帧 50mm 的情况：50/4 向上取整是 13 步，全在同一个 `driveTo` 调用里同步完成。JS 侧单次 `solveKin` 典型 5–20 次迭代、几十到几百微秒（`M.ms` 有实测），整个 `driveTo` 最坏 2–5ms——在 16ms 帧预算内，所以视觉上是**即时贴合**，用户看到的是直接跳到新姿态，不会有中间动画。极端情况：如果拖快到出现某中间步 40 次迭代没收敛到 2e-7，该步以当前残差继续走下一步，末步的 260 次兜底；如果末步也失败，`M.ok=false`，读数条上会体现为该帧指标异常——但拖拽链路上我没有专门的失败告警 UI，这是可以改进的点。

**5. [难度5] `solveKin` 的收敛判据是什么范数？`residual()` 为什么取 max 而不是 L2？**

**回答**：**无穷范数（max），单位 mm。** `residual(M,drvZ)` 遍历 coreLinks 白名单里 `type==="R"` 的杆，取 `abs(当前杆长 - L0)` 的最大值，再加轮心 Z 驱动残差 `abs(WC.z - drvZ)` 一并取 max。

(a) 单位是毫米——整个坐标系是 mm 制（`stepDyn` 里 `g=9810` mm/s² 也印证）。两套阈值职责不同：`tol=2e-7` mm 是**迭代内提前退出阈值**（极严，防止残差还在抖就退出）；`res < 0.025` mm 是**求解成功判定**（`M.ok`），宽容得多——投影迭代法的现实精度就是百分之几 mm 量级，用 2e-7 判成功会大量假失败。

(b) `(it&3)===3`：每 4 次迭代才算一次残差。`sweepProj`（连杆闭环 + 转向节刚体 + 摇臂闭式解）是大头，residual 本身相对便宜但也不白给；省掉约 75% 的残差计算。敢隔 4 次查的原因：迭代是收缩映射，残差单调下降趋势为主，两次检查之间多做 3 次投影只会更接近解，不会跳走；退出条件最多晚 3 次迭代触发，代价可忽略。循环退出后再无条件算一次 residual 写进 `M.res`，保证最终值准确。

(c) 简历表述需要精化，我主动说清楚：JS 侧投影迭代解的是**等式约束组**（每根刚性杆长度=定值 + 轮心驱动），逐点把违约位置投影回合约流形；Python 侧 `pose.py` 用 SciPy TRF 解**非线性最小二乘**（残差平方和目标），是带信赖域的通用求解器。两者问题定义不同、范数不同、精度等级不同——JS 是毫秒级近似解，Python 是高精度解。关于 parity 我要纠正题目的假设：`tphys_parity.cjs` 校验的**不是** solveKin vs TRF 的节点坐标，而是**前端内置 TPHYS 简化动力学（JS）与后端 `transient.py`（Python）的赛道瞬态一致性**——脚本用 Node `vm` 从 allinone.html 里切出 `const TPHYS = (function(){...})()` 闭包在沙箱里跑，输入 output.json 对比两边 summary（audit D1 P0-3，commit 066ac6f 记录了当时结果：v_end 13.00 vs 13.0 m/s、路程 141.3m、0.662g、滑移角 1.39°，基本逐位一致）。JS↔Python 运动学层面的校验靠的是同一组测试输入下人工比对 sweep 行，没有自动化脚本——这是我想补的坑。

**6. [难度5] 四视口的"联动"机制：重算投影还是共享数据？每帧绘制顺序和数据流请完整说一遍。**

**回答**：**联动 = 全局单份数据 + 每帧全量重绘，不是消息广播，也没有观察者模式。** 完整数据流：`loop(ts)` → `updateSweeps()`（140ms 节流的 K&C 扫掠）→ `simulate(dt)`（kin 模式下对 FR/RR 驱动到目标轮程，mirror 开启时 FL/RL 也各跑一遍 `driveTo` + `metrics`）→ `drawAll()` → `drawPlots()` → `UI.sync.forEach(f=>f())`（读数条/按钮态回填）。

(a) 确认，且说得更准：`VW` 数组里每个视口持有自己的 canvas、ctx、`s/cx/cy`（正交）或 `az/elv/dist/tgt`（透视）以及 `bx/by` 基向量；机构数据 `SIM.FR/FL/RR/RL` 是全局唯一一份，四个视口画的是同一份节点坐标在不同相机下的投影。

(b) `drawAll()` 每帧全量：`const sc=buildScene(); PICK.length=0; VW.forEach(v=>drawView(v,sc))`——`buildScene()` 每帧重建模型空间图元数组，四个视口共享这份图元、各自投影。没有脏区、没有增量重绘，也没有"只重绘鼠标所在视口"。没做的原因：单帧绘制成本 3–7ms 已经在预算内，而拖拽联动恰恰要求四视口同时刷新（正视图拖、另外三视口要同步看到姿态变化），按视口脏化省不了主路径，反而增加失效模式。真正该做的优化是"机构没变时跳过 buildScene 重投影"——几何缓存我在爬坡 stage 里做过（`deb079f` 那次 commit 专门修了 stage 打开时每帧重建 buildScenePRO 的帧率杀手），主视图还没做。

(c) 代码事实：`updateSweeps()` 开头 `if(now-SIM.lastSweep<140)return;`——140ms 节流，然后 `runSweep(..., 45, ...)` 前后轴各 45 步。扫掠和拖拽在同一线程（主线程 rAF），没有 Web Worker。拖拽期间扫掠最多每 140ms 插入一次 90 步（2×45）的批量求解，每次几十毫秒，实测帧率会掉一下再回来——能感觉到顿挫但不失控。主动承认：**没把扫掠挪进 Worker 是已知短板**，是排期取舍，不是不知道。

**7. [难度5] 拾取：`pickNode()` 是屏幕空间最近邻，阈值 `bd=90`。这套拾取的盲区在哪？**

**回答**：**是 2D 距离场最近邻，不是射线投射。** `bd=90` 是平方像素距离的初值，即命中半径 √90 ≈ 9.49px，循环里 `d=(p.x-mx)²+(p.y-my)²`，比初值小就更新。这个半径比 3.5px 的节点绘制半径大一倍多，是给鼠标hover留的容差。

(a) `PICK` 数组在**绘制阶段**填充：`drawView` 处理 `"n"` 型图元时，`const A=P2(v,o.p); if(!A)continue;`——**先投影，投影成功才 `PICK.push({x,y,id,v,p,sx,axis})`**，且每条记录绑定了所属视口 `v`（`pickNode` 里 `if(p.v!==v)continue;`）。所以近平面后被丢掉的节点**不进 PICK、完全不可拾取**——这就是题目问的盲区之一：透视视图里转到某些角度，个别硬点会既画不出来也点不到。`PICK.length=0` 在每帧 `drawAll` 开头，所以 PICK 的有效期只有一帧，拾取和渲染严格同帧。

(b) 重叠时选**平方距离更小者**，没有深度消歧。正视图里前后轮硬点 Y 重合时，镜像侧节点根本不画在同一个机构里（FL/RL 的节点有自己的 yOff），同一机构内前后重叠的场景实际少见，但我没有做按深度排序的消歧是事实；用户靠切视图或关闭 mirror 显示来规避。

(c) 代码事实：`mousedown` 里 `if(e.button===0 && hit && v.type==="o")` 才进入 hp 拖拽；透视视口左键直接进 `"orb"` 旋转。根因是**屏幕位移→世界位移的反解在透视下不唯一**：正交视图里，`da=(dx)/v.s` 给出视图平面内毫米位移，配固定基向量 `bx/by` 唯一合成世界向量；透视下同一段屏幕位移对应的平面深度 z 未知，硬点沿视线移动和横移可以产生相同的屏幕位移，无法反解。原理上的正解是拾取射线与"过该点、法向为视线方向"的拖拽平面求交——射线是 `eye + t·dir`，与平面 `dot(X - p0, fw) = 0` 联立解 t，交点反算世界位移。这个方案我推过，没实现，因为透视视图被产品定位为观察视图，正交三视图已覆盖拖拽需求。

**8. [难度4] 拖拽把屏幕像素位移转世界坐标的公式是什么？**

**回答**：代码原文：`da=(e.clientX-d.x0)/v.s, db=-(e.clientY-d.y0)/v.s`，然后 `w=[bx[0]*da+by[0]*db, bx[1]*da+by[1]*db, bx[2]*da+by[2]*db]`。`v.s` 的几何意义是 **px/mm**（每毫米多少像素），除以它把像素位移换算成视图平面内的毫米位移；Y 取负是因为屏幕 Y 向下、世界 Z（或视图 by）向上。正交视图下 `bx/by` 是互相正交的单位基向量且与视线垂直，平面内位移与法向解耦，所以这个映射是精确的。`v.s` 由 `fitView` 按包围盒算出，滚轮缩放 clamp 在 [0.02, 15]，即 1mm 从最小 0.02px 到最大 15px。

(a) 滚轮：`f=Math.pow(1.0015,-e.deltaY); v.s=clamp(v.s*f,0.02,15)`。用幂函数因为 `deltaY` 是离散大步长（一格通常 ±100），线性乘法会产生跳变感，指数映射保证"相同滚轮量 → 相同缩放比例"，任意位置手感一致（对数均匀）；1.0015 这个基数调到一格滚动约 14% 缩放，跟手不窜。clamp [0.02,15] 的下限防止缩太小时拾取半径相对内容失效、数值显示精度崩坏，上限防止缩太大后一像素位移就打出 ±15mm 的坐标跳变、拖拽不可控。

(b) `Math.round((d.base[k]+w[k])*10)/10`——量化到 0.1mm。两个动机：显示侧硬点表格和状态栏固定显示 1 位小数，量化让 UI 显示与真实存储严格一致，不会出现"表格显示 260.0 实际是 260.0492"的错位；求解侧避免拖拽中浮点尾数（1e-13 量级）被当成"坐标变了"触发无谓的机构重解和 sweep 失效标记。

(c) 镜像侧（sx=-1）拖拽时 `if(d.sx<0)w[0]=-w[0]`。因为 FL/RL 机构复用 front/rear 的同一份硬点表，镜像侧的世界 X 与屏幕映射方向相反：用户在屏幕上向右拖，镜像机构的世界 X 应该减小才符合直觉（对称逻辑），所以 X 分量翻符号。Y（沿车轴方向）和 Z（竖直）不随左右镜像翻转——镜像只镜 X，这是机构建模的约定，拖拽映射必须遵守同一约定。

**11. [难度4] 你的视口自适应：为什么把 DPR 钳到 2？**

**回答**：`sizeView` 里 `const dpr=Math.min(2,window.devicePixelRatio||1)`。钳 2 的动机是**填充率和显存成本**：4 个视口同时重绘，物理像素数是 `(w·dpr)×(h·dpr)`，dpr 从 2 到 3 是 2.25 倍像素量、从 2 到 4 是 4 倍——四个视口相乘很可观，而超过 2 的 DPR 对线框图的视觉增益边际递减（线条已经小于 1 物理像素宽）。4K 屏 + 150% 浏览器缩放时 `devicePixelRatio` 是 1.5，钳制值就是 1.5 本身，canvas 物理分辨率 = CSS 尺寸 × 1.5——**最终是 `Math.min(2, devicePixelRatio)` 和视口 CSS 尺寸共同说了算**，浏览器缩放通过 devicePixelRatio 进入这条链。

(a) `v.cv.width = w*dpr`（物理像素）与 CSS 尺寸 `w` 不一致时，若不处理，绘制会被拉伸模糊。我靠 `v.ctx.setTransform(dpr,0,0,dpr,0,0)` 把绘制坐标系抬回 CSS 像素——所有绘制代码（含 `P2` 输出）只面对 CSS 像素坐标；鼠标侧用 `getBoundingClientRect()` 返回的也是 CSS 像素。两个坐标系天然同一，拾取/拖拽不需要任何额外换算。

(b) `if(v.w<20||v.h<20){v.s=0.5;return;}`，注释 `(2026-08-24)`。当时的 bug 现象：页面初始化时 `ResizeObserver` 首次回调早于布局完成（或最大化切换瞬间），视口 rect 是接近 0 的占位值，`fitView` 用 `v.s=Math.min((v.w-30)/...,(v.h-34)/...)` 算出负数或极小值，四个视口定型在烂视角，用户必须双击 fitView 才能救回来。加这个守卫让过早触发的 fitView 直接跳过，等后续真正布局完成的 resize 事件再算。

(c) `toggleMax` 里 `setTimeout(()=>VW.forEach(sizeView),0)`：因为给视口元素加 `.mx` class 后，CSS grid 布局的 reflow 是异步的——同步调 `sizeView` 拿到的 `getBoundingClientRect()` 还是旧布局的尺寸，量出来的 w/h 是错的。`setTimeout(...,0)` 把测量排到宏任务，等浏览器完成重排后再量，拿到的才是最大化后的真实尺寸。这是标准的"改样式→测尺寸必须让出执行栈"问题。

**13. [难度4] 引擎通信层：四个 AbortController 超时为什么差 30 倍？**

**回答**：代码事实：`/api/v3/health` 探活 **4000ms**（engineConnect）、K&C 三工况 **60000ms**、整车 chassis **90000ms**、赛道 `simulate_track` **120000ms**——四个 `new AbortController()` + `setTimeout(()=>ctl.abort(), N)`。超时与后端计算量成正比：health 是纯探活；K&C 是 3 工况 × 45 步 × TRF 求解；chassis 是整车准静态 + 工况矩阵；赛道是 dt=0.01s、sim_time 25s 即 **2500 个时间步**的瞬态积分。给足量级余量又保证失败可感知，而不是统一一个"够大"的超时让 health 挂 2 分钟。

超时后 UI 状态：fetch 抛 AbortError，进 catch，`setKcStatus`/`setChStatus`/`setTrkStatus` 写红色错误信息（如"仿真失败：…"），按钮文字在 finally 里复位（如 `btn.textContent="运行赛道仿真 RUN"`），`ENG.ok` 不因此翻转——超时不代表引擎死了，下次连接 health 再判。用户恢复路径：看状态栏文案 → 改参数重试，或断开重连。

(a) 请求期间**不锁 UI**。用户在 60s K&C 期间继续拖硬点，前端 S 层会变，而响应回来时会基于"请求时的 payload"覆盖 SIM/图表——**存在请求在飞、状态已变的竞态**，我承认。当前靠"分析按钮与拖拽画布分属不同面板 + 结果写入独立结果区"把冲突面缩到最小，但严格说响应可以把过期数据写进曲线区。正确修法是请求序号 + 到达时比对代际，过期即丢——设计清楚但没实现，诚实认账。

(b) AbortController 只用于超时中断，**没有请求去重/取消旧请求**。四个接口都是按钮显式触发、低频（K&C/整车/赛道一次一个），分析接口去重收益低；真正高频的是拖拽，而拖拽根本不走网络（见第 16 题），所以这个问题在我架构里被源头消解了。

(c) `ENG.ok` 切换是**手动连接 + 失败自动置否**：`engineConnect()` 发 health（4s 超时），成功 `ENG.ok=true` 并把状态栏按钮改"断开引擎"；失败 `ENG.ok=false` 并提示"连接失败 → 本地 JS 仅运动学/几何扫掠；K&C/整车/赛道需引擎"。没有自动重连、没有自动降级探测——每个分析入口（K&C/chassis/track）开头都检查 `if(!ENG.ok)` 然后提示未连接，功能上等价于"断开时自动用内置 JS 继续干活"，但连接动作本身是用户显式的。

**14. [难度5] "无框架裸写状态管理"：S/SIM/UI 的读写权限？`UI.sync` 是什么模式？**

**回答**：三者职责与数据流向是单向的：`S` 是**用户输入态**（硬点坐标、刚度、工况、播放开关、travel/rack），只有交互回调写它；`SIM` 是**求解派生态**（四个机构、扫掠结果、几何极限、指标），只由 `rebuild()/refreshDerived()/simulate()` 写；`UI` 是**交互瞬态**（`{hover:null,selHP:null,drag:null,ro:{},sync:[],plots:[]}`），只有事件处理器写。方向：S 改 → `rebuild()` 重建机构并 `refreshDerived(true)` → 主循环读 SIM 画。反向只有一处：`refreshDerived` 会把算出的行程极限回写 `S.trMin/S.trMax`（滑条范围），这是有意的派生回填。

`UI.sync` 我先纠正定性：它是**每帧全量轮询的同步回调数组**，不是发布订阅、更不是响应式。`loop()` 每帧 `UI.sync.forEach(f=>f())`，另外在 `mousedown`/面板切换等时机也有手动 `forEach` 立即刷新。

(a) `refreshDerived(full)` 的 full 控制**几何极限查找**要不要重跑：`if(full||!SIM.geoF) SIM.geoF = findLimits(...)`。拖硬点时走 `rebuild()` → full=true（硬点变了极限必须重找）；滑条调刚度/质量走 `refreshDerived(false)`（几何没变，跳过 findLimits，只重跑扫掠和弹簧预紧）。判据就是"被改的量是否影响行程极限"。

(b) 改了 `S[axis].hp[id]` 之后谁更新：不靠依赖追踪，靠**约定注册**——硬点表格行注册 `UI.sync.push(()=>{if(document.activeElement!==inp)inp.value=fmt(...)})`，按钮注册 `()=>bt.classList.toggle("on",...)`。每帧全量跑几十个轻量 DOM 文本/类名写入，单个 <0.05ms，总量 <1ms——测过（Performance 面板里 UI.sync 段不显眼），没成为性能问题。它"能跑"的本质是回调数几十个且全是 O(1) 写，规模再大一倍就该改脏标记了。

(c) 加 Undo/Redo 的真实成本：我的 `deepClone = JSON.parse(JSON.stringify(obj))` 已在 `takeBaselineSnapshot` 里用于快照 S.front/rear + swF/swR/qsRes。Undo 会撞上三个问题：一，JSON 深拷贝丢 `undefined`/函数/引用关系——S 层是纯数据能扛，但 SIM 机构含迭代状态和索引别名（`M.idx` 指向节点数组下标），整快照 SIM 又大又没必要；二，每帧拖拽都写 S.hp，Undo 栈要么按拖拽手势合并（mouseup 时压栈），要么爆炸；三，JSON 序列化 348KB 文件里那套状态的开销在毫秒级，可接受但要节流。正确刀法：**只对 S 层（可序列化的输入态）做命令栈/快照栈，SIM 是纯派生、undo 后 rebuild 即可**——结构上我的单向数据流恰好支持这个，工作量集中在拖拽手势合并，不是伤筋动骨，但也不是"加个数组"那么轻。

**16. [难度5] 内置 JS 引擎和 Python 引擎在拖拽链路上的延迟差多少？**

**回答**：数字：JS `solveKin` 单次 **0.05–0.3ms**（5–20 次迭代，`M.ms` 实测计时），完整 `driveTo` 含分步 **2–5ms**；本地回环 `POST /api/v3/solve/pose` 端到端 **5–30ms**（JSON 序列化 + FastAPI 路由 + TRF 求解 + 响应解析）。前者在 16ms 帧预算内游刃有余，后者单次请求就已经吃掉 1–2 帧、还叠加网络/序列化抖动——**拖拽联动必须在 JS 侧闭环**，这是硬约束不是偏好。

(a) 诚实答案：文档里那段话（`LABSUS_Technical_Doc.md` "数据流式传输与状态防抖"节："**部分高频接口可能**在前端或者路由层附加了极低阈值的节流逻辑"）**在代码里找不到系统实现**。我在自己代码里能指认的节流只有一处：`updateSweeps()` 的 `if(now-SIM.lastSweep<140)return;`（140ms 节流 K&C 扫掠），以及拖拽本身不走网络所以没有"solve 高频请求"可节流。文档用了"可能"这种 hedged 措辞——它是对架构的展望性描述，写在了实现前面。**文档表述超前于代码，我承认**；这也是我后来做代码审计（79714c8 里"honest K&C copy"）修正文案的原因。正确顺序应该是先有实现再有文档断言。

(b) 无状态引擎约定每次携带完整 base 硬点：`chassisPayload()` 把整车参数 + 前后轴各 15 个硬点 + 工况序列化为 JSON，量级 **1–3KB**，`JSON.stringify` 在这个尺寸下是微秒级，可忽略。真正贵的是 FastAPI 侧 Pydantic 校验和 TRF 本身。

(c) 把拖拽求解放 Python 侧：WebSocket 推帧也达不到同体验。卡点算术：帧预算 16ms，Python 侧单次 TRF 求解 1–10ms 看似可行，但要叠加上 WebSocket 往返（本地 0.5–2ms）、JSON 编解码（每帧）、FastAPI async 调度抖动和 Python GC——p99 轻易破 16ms，表现为拖拽偶发卡顿，比稳定的 2–5ms JS 闭环体验差一档。而且后端是同步求解器，要撑高频还得加任务队列。结论：**交互闭环留 JS，Python 做离线高精度**，这个分工是延迟算术决定的，不是技术偏好。

**17. [难度5] 透视投影 `P2` 里 `if (z < 80) return null`——穿越近平面的杆件最终画出来是什么？你修过没有？**

(a) `projLink/projHinge/projBody` 等是**模型空间**求解（`solveKin` 链路），不产生 null；null 只在绘制层 `P2` 产生并就地中断，不向上传播——这保证了求解永远拿到完整坐标，视觉缺失不影响数值。

(b) 没有远平面，没有主动屏幕外剔除——超出 canvas 的图元照画，交给 canvas 原生光栅裁剪。代价是白白光栅化，收益是省 CPU 判断，几百个图元量级下我选了后者。

(c) `camIso` 里 `v.rt=nrm(cross(v.fw,[0,0,1]))`：当视线接近竖直（elv→±90°），`fw` 与世界 Z 平行，叉积趋于零向量，`nrm` 归一化除以近零长度 → `rt` 变 NaN → 整视口花屏。**是的，orb 拖拽里 `v.elv=clamp(...,-85*D2R,85*D2R)` 就是为了掩盖这个退化**——clamp 到 ±85° 给叉积留了 `cos(85°)≈0.087` 的安全余量。通用正解是接近极点时切换 up 向量特判（如 `dot(fw,[0,0,1])` 超阈值改用 [0,1,0]），或直接上四元数轨道相机。75aef1d 那次 stage 相机 NaN 修复里我加过"degenerate-z guard"，说明我清楚这个坑，主视图只是选择了 clamp 这种够用的方案。

**18. [难度4] `projBody` 用四元数极分解——为什么不用 SVD？**

**回答**：`projBody` 干的事：转向节（knuckle）是刚体，约束系统只给出其上若干点（LBJ/UBJ/WC/TRO）的新位置，需要重建刚体姿态。做法：对加权外积矩阵 `A[i][j] = Σ w·r_i·r_j`（r 是节点相对质心的参考坐标）做极分解，`polarQ(A,c.q,14)` 最多 14 次迭代求**最接近 A 的正交旋转 R**，再用 R 把参考坐标搬运到新位置。不用 SVD 因为：极分解只需旋转因子（A = R·S 的 R），迭代法（Higham 式，每步 `q ← qNorm(qMul(qAA(ω/|ω|,|ω|), q))`，ω 由叉积和构造）每次迭代成本远低于一次 SVD，且我有极好的初值——上一帧的四元数，通常 2–4 次迭代就收敛（`w<1e-13` 提前退出），14 只是上限。

(a) `c.wt` 来自节点质量：`const wt=ids.map(k=>Math.max(n[k].m,1e-3))`，而 `n.m` 是 `HP_META` 第 6 列的代理质量（LBJ 2.0、UBJ 1.5、WC 10.2、TRO 0.9、STRUT_OUT 1.2…kg 量级）。**这些不是实测物理质量**，是"轮心最重、球头次之"的工程代理权重，作用是让姿态拟合偏向高惯性点、抑制轻点噪声；`1e-3` 下限是防零权重除零的数值护栏，不是物理值——这点我不粉饰。

(b) 用四元数不走欧拉角，gimbal lock 在这条路径上**不存在**：极分解迭代需要在旋转流形上做连续小旋转复合（`qMul`），四元数乘法天然无奇异、可归一化回单位球；欧拉角复合会遇万向锁，旋转矩阵迭代则会漂移出正交群需要反复正交化。四元数是这个迭代算法的原生表示。

(c) 14 次不收敛（A 接近奇异，对应**节点集共线**——正常约束系统不应发生，因为转向节四点不共线）时：返回的 R 不完全正交，搬运后的节点相对距离失真 → 杆长残差变大 → 末步 `solveKin` 的 `residual` 抓到 `res≥0.025` → **`M.ok=false`**，`M.res/M.iter/M.ms` 记录现场。UI 上该帧指标可能出现 `fmt()` 对非有限值显示"--"。链路是通的，但我不为极分解本身设单独告警，失败归因要靠 res 数值反推——可改进。

**20. [难度5] `residual()` 只检查 coreLinks 白名单——白名单外的从动件不可达时 `M.ok` 还会 true 吗？**

**回答**：先把白名单念准：`coreLinks = ["LCA_F-LBJ","LCA_R-LBJ","UCA_F-UBJ","UCA_R-UBJ","KINGPIN","TIEROD","KNK_L","KNK_U","KNK_T1","ATT_F-ST_O","ATT_R-ST_O","ATT_B-ST_O","RA-SI","RB-SI","RA-RD","RB-RD","SI-RD"]`，且只查 `type==="R"` 的杆。**推/拉杆（STRUT_OUT 到摇臂输入点）的长度不在 residual 里**——它由 `projRockerStrut` 的闭式解（铰链四杆三角方程）"解"出来而不是"约束"住；阻器长度同样是派生量。白名单覆盖主运动学闭环，从动输出不参与收敛判定。

(a) 会的——这正是我承认的**静默吞错缺陷**：`projRockerStrut` 里 `const cosPsi=clamp(C/hyp,-1,1)`，当几何上杆长不可达（|C/hyp|>1，对应摇臂转轴到外点距离与杆长的三角关系无解）时，acos 被强行夹回合法域，解出的是一个"最近的假姿态"——机构实际断裂，但残差检查查不到这条路径（它的杆长不在白名单），**`M.ok` 仍返回 true**。UI 上唯一线索是摇臂角度 `rck.angle` 出现突兀值、减振器行程读数异常。正确修法我清楚：`projRockerStrut` 返回可达性标志，或把 clamp 前的 |C/hyp|-1 超界量并入 residual 做软告警——没做，是排期而非认知问题。

(b) branch 翻转：`branch = phi>=0?1:-1` 固定按 φ 符号选三角解分支，配合分步延拓（4mm 步长）维持连续性。真发生分支跳变时用户看到**机构姿态瞬间跳变**（摇臂翻边、减振器穿模），指标曲线出现阶跃尖峰。我**没有系统检测分支连续性**（比如对比相邻步的 theta 突变量超阈值即标记）——这是列在待办的正确修法。当前防线只有延拓步长本身，它把跳变概率压低但没有归零。

(c) 真实案例：调 FSAE 预设大 heave（+65mm）时出现过 UCA 收敛到"翻转装配"——轮心到位但上球头跑到另一侧，外倾角瞬间跳十几度。当时的修法就是两层：确认 `driveTo` 的分步延拓在位（早期版本一步到位最容易触发），以及 `resetMech` 保证初值在正确分支附近。这教会我：**投影法的装配分支稳定性 = 初值管理 + 步长管理**，两者我都做了，但缺显式检测是诚实的短板。

**21. [难度3] 主循环 `dt = Math.min(0.045, ...)`——这个 45ms 上限防什么？**

**回答**：防 **tab 后台节流后回前台的巨帧**。浏览器对后台 tab 把 rAF 降到 1Hz 甚至冻结，切回来首帧 `ts-_last` 可能是几秒，直接喂给 `stepDyn` 积分器（半隐式欧拉，h=dt/10）一步就数值爆炸——45ms clamp 配合 `stepDyn` 的每子步速度钳制（`sp>2e4` mm/s 归一化）构成防爆双保险。`S.play=false` 时循环照跑：渲染、视角操作、拖拽、hover、读数刷新、FPS 统计都依赖主循环，暂停只停 `S.t` 推进和激励发生，不停绘制。

(a) 多 rAF 链是 stage 隔离的历史产物，代码注释直说了动机："爬坡舞台打开时挂起主仿真，**避免双写 SIM**"（`simulate` 里 SLOPE_STAGE/SKIDPAD_STAGE active 时直接 return 并续帧）。主循环在 stage 激活时只做 `requestAnimationFrame(loop)` 空转保活，stage 有自己的 `stageTick/slopeStageLoop`。为什么不合并成一个调度器：stage 是后加的重度功能（15-DOF 爬坡、5 相机赛道舞台），有自己的时间步和渲染管线，合并意味着重构主循环的职责划分；代价是双 rAF 各自烧一份帧回调 + 切换瞬间有双写风险（注释即证据）。承认是技术债，但被 typeof 守卫和 return 顺序控制住了。

(b) 后台 1Hz 节流时：主循环 dt 被 clamp 到 0.045s，仿真时间以最大 45ms/帧龟速推进——**仿真时间与真实时间脱钩**（慢放而非跳变），这是有意的失真方向：宁可慢不可炸。彻底的正解是固定步长累积器（fixed timestep accumulator：按真实时间累积、按固定 h 消费、渲染插值），我没做，现状是"clamp + 龟速"的务实解。

**22. [难度4] 前端的角色边界：4-Post 的 `stepDyn` 和赛道 `simulate_track` 各在哪跑？为什么不同？**

**回答**：边界分明：**4-Post 台架/爬坡/绕桩的动力学积分在前端 JS**——`stepDyn(M,dt,rack,tSim,axis)`，半隐式欧拉；**赛道瞬态在后端 Python**（`/api/v3/chassis/simulate_track`），前端只回放（`TRK.playing`）。选择不同的依据：4-Post 是交互式调参场景，用户拖滑块要看毫秒级响应，JS 侧的 15 节点准动力学（弹簧/双向阻尼 `cB/cR`、二次 bumpstop `kBS·x²/20`、轮胎 `kT·pen+cT` 接触、每帧 10 子步 × 每子步 12 次约束投影）够用且必须本地；赛道瞬态含 MF 复合滑移轮胎 + 滑移松弛长度 + 传动包络 + 空气动力学，JS 侧无此实现、也无需交互级实时——算一次看报告，异步 120s 可接受。

(a) `stepDyn` 里 `const NS=10, h=dt/NS`——**有子步进**：每帧 10 个子步，每子步重力/弹簧/阻尼/bumpstop/轮胎力累加 → 积分 → 12 次 `sweepProj` 约束投影。dt 是被 clamp 到 0.045s 的帧 dt，所以帧率掉了子步长变粗（h 最大 4.5ms），精度降但稳定（配速度钳制）——不是"绑帧率就炸"，但确实是"帧率影响积分精度"，固定步长累积器是正解（同第 21 题）。

(b) 赛道是**回放不是实时推进**：后端一次算完 2500 步 trace（dt=0.01s、sim_time 25s），前端 `trackStep(dt)` 按播放时钟推进索引：`adv=Math.max(1,Math.round(dt*TRK.speed/TRK.res.t[1]||0.01))`——TRK.speed 倍速直接缩放每帧前进的 trace 步数，t[1] 是 trace 步长。为什么回放：确定性（可 scrub 拖动时间轴、可 loop）、前端零求解负担、且 3D 舞台相机跟随需要"已知未来轨迹"才能拉好机位。

(c) 前端 K&C 查表：`trackPayload()` 里 `kc_luts={front:lut(SIM.swF),rear:lut(SIM.swR)}`，lut 就是扫掠的 45 行 `{travel,toe,cam}` 原始数组，后端按 travel **线性插值**（我前端自己的 `sampleSweep` 也是线性：区间内 `t=(tr-R[k-1].tr)/(R[k].tr-R[k-1].tr)`，端点截断）。45 步对应约 3mm travel 分辨率，camber/toe 曲线在这个粒度上局部线性假设的误差 <0.05°——对力平衡是二阶小量，我做过对比（加密到 91 步 summary 变化在容差内），但没把它做成可配置参数，是默认 45。

**23. [难度4] `serve_nocache.py` 存在的意义？目标浏览器矩阵？**

**回答**：它是 30 行的标准库静态服务器（`http.server.ThreadingHTTPServer`，127.0.0.1:8921），唯一特殊之处是每个响应加 `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` + `Pragma: no-cache`。防的具体 bug：**开发期改了 348KB 单文件、浏览器刷新却拿磁盘缓存的旧版本**——单文件 HTML 这么大，Chrome 对它的启发式缓存很积极，我当时改代码不生效排查了好几次才发现是缓存，写了这个服务器根治。

(a) 双击 file:// 直接打开 allinone.html 可用、fullchassis.html 不行，根因：fullchassis 需要 `fetch(ENG.url+"/api/v3/...")` 连引擎，file:// 下 origin 是 null，浏览器把 fetch 当跨域请求禁掉（CORS 无从谈起），控制台直接报错；allinone 内置 TPHYS（commit 066ac6f 的设计目标就是"standalone track stage works with zero backend"），零 fetch 需求，file:// 下唯一受限的只有 localStorage 在某些浏览器的分区行为，功能不受影响。所以部署矩阵是：断网/赛场用 allinone 双击，有引擎用 fullchassis + serve_nocache.py 或任意静态服务。

(b) 如上——no-cache 防的是"改了不生效"的开发期缓存 bug，不是为了生产部署（生产直接 no-store 也无妨，单文件自包含）。

(c) 兼容矩阵诚实版：**Chrome/Edge 深度实测，Firefox 基本验证，Safari 没测过**。用到的 API（ResizeObserver、AbortController、可选链、`& 3` 位运算、import 无）都是 Chrome/Edge 全支持、Firefox 支持的基线特性，位运算无兼容问题；Safari 的 Canvas 2D 文本渲染差异和 devicePixelRatio 行为我没有第一手验证，不做承诺。

**24. [难度5] 把四视口从 Canvas 2D 迁到 WebGL：三块各要重写什么？工作量排序和最难的坑？**

**回答**：先报拾取点数量级：`HP_META` 15 硬点/机构，四视口绘制时每视口约 15–30 个节点图元进 PICK（mirror 开时翻倍），**总量 <100**。工作量排序（难→易）：**文字标注 > 线宽 > 拾取**。结论先行：我的答案是"**当前规模不值得迁**"——Canvas 2D 在我的帧预算里占 3–6ms，瓶颈不在光栅化；迁移的真实收益只有深度一致性（解决第 9 题的排序错序）和更细的线宽控制，为这个上 WebGL 是为迁而迁。

(a) 线宽：现在 `ctx.lineWidth=o.w` 是屏幕像素语义，Canvas 2D 原生支持任意宽度；WebGL 的 `gl.lineWidth` 宽于 1 在多数实现（尤其 Windows ANGLE）不可用，替代方案是把每条线展开成面向相机的三角带/实例化四边形（billboard line），或者接受 1px。我的图元里大量 2–3px 线（弹簧、轮胎轮廓），三角带展开意味着 buildScene 的图元模型要加一整层"屏幕空间膨胀"几何生成。

(b) 文字：现在 `TX` 图元直接 `ctx.fillText`（HUD 标注、尺寸线文字、坐标标签几十处）；WebGL 文字要 SDF 字形图集或贴图 atlas，工作量最大且边界情况多（中文！我的标注全是中文，字形集比 ASCII 大一个量级）。**务实方案就是混合架构**：WebGL 画几何 + 一个叠在上面的透明 Canvas 2D 画文字和 HUD——这其实是承认 Canvas 2D 在 2D 语义上不可替代。

(c) 拾取：<100 个点，**CPU raycast 足够**，GPU id-buffer（渲染时写 id 到帧缓冲再 readPixels）是杀鸡用牛刀且引入 readPixels 同步 stalls。现有屏幕距离场拾取在 WebGL 下甚至可以原样保留（投影函数换成矩阵变换即可）。

最难的坑总结：不是性能，是 **Canvas 2D 的"2D 语义"（像素线宽、fillText、globalAlpha 叠加）在 3D API 里全部变成几何问题**。迁移决策上，我给自己定的判断标准是：只有当图元量级上到万级三角形（比如要做完整车壳网格渲染）时，WebGL 才从"可选"变"必须"。

**25. [难度4] 最后一题：把"原生 Web 前端与计算引擎双实现，四视口硬点拖拽实时联动"改成精确表述。**

**回答**：三句话，我主动降噪，不等追问：

(a) **"原生"的精确表述**："前端为零运行时依赖的**手写 Canvas 2D 软渲染**：自推正交/透视投影、屏幕空间最近邻拾取、四元数代数 + 极分解刚体重定向，无 Three.js、无框架、无构建链；明知其裁剪与深度排序为已知简化（近裁剪丢线、无画家排序），量级上经实测仍留有帧预算余量。"

(b) **"双实现"的精确表述**："计算引擎双实现是**精度分层**而非冗余备份：JS 侧闭式投影迭代提供毫秒级交互闭环（成功判据 0.025mm），Python/FastAPI 侧 SciPy TRF 提供高精度 K&C/整车/瞬态求解；两侧的赛道物理（TPHYS ↔ transient.py）由 `tphys_parity.cjs` Node harness 校验到摘要量级一致（v_end 13.00 vs 13.0 m/s、0.662g），运动学层面的一致性校验尚无自动化，是已知欠账。"

(c) **"实时联动"的精确表述**："四视口联动 = 全局机构数据单份共享 + rAF 每帧全量重绘；硬点拖拽是 JS 侧毫秒级真重解（continuation 分步延拓，非插值）；但 K&C 扫掠是 140ms 节流批处理（无 Worker 隔离），赛道仿真是后端异步计算后倍速回放——三个'实时'等级不同，简历把它们打包成一句话确实过度了，我承认。"

简历这句话我当初的辩护是"每一半单拎出来都成立"，但打包陈述会诱导听众按最高等级理解每一半——面试语境下这就是夸大。以上三句才是我对这个系统的诚实描述。
